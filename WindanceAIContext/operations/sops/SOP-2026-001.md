# SOP-2026-001 — Submit and publish an operational SOP

- Status: Vetted (documentation procedure)
- Owner: Archivist; technical partner: Forge
- Trigger: A repeatable process is learned or changed.
- Review due: 2026-12-18, or earlier after workflow changes.
- Search terms: SOP submission, runbook, process documentation, staff knowledge transfer

1. Read START_HERE and current operating policy. Check INDEX.md and existing runbooks to avoid a duplicate.
2. Create a Draft using TEMPLATE.md in the canonical operations/sops directory. Assign a stable ID and one owner. Record scope, prerequisites, steps, expected outcomes, verification evidence, recovery and limitations. Exclude credentials and private content.
3. Add the submission to INTAKE.md and INDEX.md. Request Archivist's structure/index check and Forge's technical check through durable staff tasks. Limit reviews to the specific document and evidence; do not authorize unrelated execution.
4. Address findings. Preserve real review task references and outcomes. Only mark Vetted after both reviews substantiate the actual revision. If evidence is missing, retain Needs evidence.
5. Update linked current-state/decision records when appropriate. Run scripts/publish-windance-context.ps1 -PushGit from the canonical package.
6. Confirm publisher success and Second Brain retrieval of the SOP ID/title. A copied file or a Git commit alone is not completed publication.
7. Link the published SOP in the originating work record and set the next review date.

Verification: draft, index, intake, two review receipts and successful publication/search receipt all exist. No operational command in a newly drafted SOP is considered tested merely because the document was reviewed.

Recovery: retain prior Git revisions. Correct the canonical source and republish if a published procedure is wrong; do not delete history or rewrite Git. Escalate publication failures to Vega.
