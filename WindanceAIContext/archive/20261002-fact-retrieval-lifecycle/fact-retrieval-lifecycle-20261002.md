# Canonical fact retrieval and sharing lifecycle candidate

Extended the staged owned_fact_store with visible_facts and a transactionally coupled grant-event ledger. Production remains unchanged; the new schema has not been installed.

visible_facts requires an explicit supported principal and explicit business/personal scope selection. Owner/grant eligibility and deletion state are checked in SQL before the result limit. It reads the canonical value/source/revision; it never uses a derived vector or exported mirror. Source IDs encode owner/scope/kind/key, avoiding cross-owner and cross-scope key collision. Latest write-event order is deterministic; this is a bounded listing, not semantic ranking.

Explicit grant and revoke changes append audit events in the same transaction as access state. Repeated same-revision grants are idempotent. Corrections/deletions invalidate existing grants and record that invalidation, avoiding automatic exposure of newly supplied content. Audit failure rolls back access mutation. Event history does not contain obsolete raw fact values, though existing source references/hashes remain retained.

Eight new lifecycle tests and23existing storage/identity/sender-chain tests passed on HAL (31 total). Cases cover correction/deletion, an untouched stale-vector fixture, scope isolation, sharing/revocation, correction invalidation, audit failure, repeated grant,510foreign rows before limit, missing identity/scope, invalid limits and unique source IDs. The stale-vector fixture establishes this selector does not consult that cache; it does not prove the existing Harness or Hermes mirror cannot independently read stale content. All test data/credentials are synthetic; no model/embedding call, service change, send or Odoo request.

Existing raw conversation history/backups are not erased by fact deletion.
