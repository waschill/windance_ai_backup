# Read-only exact draft recovery contract, staged

October 2 UTC / October 1 Mountain 2026. Not connected to production creation or the intent journal yet.

Google documents a stable draft container ID while its underlying message can be replaced; sending removes the draft and creates a sent message. This means an absent draft cannot establish that creation failed. [Draft lifecycle](https://developers.google.com/workspace/gmail/api/guides/drafts)

The documented drafts.list query supports rfc822msgid, returns pagination state and draft IDs. drafts.get can return raw MIME for inspection. [Draft search](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.drafts/list), [Draft retrieval](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.drafts/get)

Proposed implementation uses a deterministic operation-specific RFC Message-ID plus a fingerprint of the exact generated plain-text recipient, subject, marker and MIME-decoded body. The staged preparation helper constructs MIME only; it makes no API calls. A read-only lookup issues at most one list(maxResults=2, no automatic retries) and one raw get, requires exactly one complete result, checks draft ID/state/thread and the exact marker/payload, and returns minimal match evidence without exposing content. It does not release a journal hold or permit a write. Extra recipients, ambiguous headers, malformed/oversized data, edited content, missing drafts, duplicates, incomplete pages and failed lookup retain a hold.

Ten synthetic adapter cases passed: exact match, no result, duplicate, pagination, changed content, wrong marker, wrong returned draft ID, no longer a draft, wrong thread and transport error. The fake adapter has no write methods. Each case performs at most two simulated reads; zero actual Gmail/model/send/create/delete calls occurred. This checks local validation and call shape, not Gmail indexing or preservation of the custom Message-ID. It is a proposed correlation mechanism, not an authentication credential or a guarantee against a compromised mailbox/client.

Integration must persist the exact marker/fingerprint before draft creation, derive mailbox/owner from trusted configuration, use bounded authenticated read transport and preserve original source identity privately for operator review. Current journal request hashes are not automatically the same as this MIME fingerprint; do not substitute them. No production draft builder/header or schema was changed. Before linking positive evidence to reconciliation, re-check the local immutable operation binding and preserve both evidence and prior ambiguity. Never use a negative search as permission to recreate; a draft may be deleted, sent, edited or not yet indexed.

Other gates remain: current mailbox owner capability, concurrent competing action paths, historical unmarked operations, user-friendly per-operation review, actual Gmail preservation checks, complete recovery and fresh deployment. The helper bounds call count and inspected payload size, not network elapsed time; transport deadlines still need enforcement. No raw business data or secrets are published. Existing staged files need no production rollback. Phase1 open; no new charges, application model usage zero, Codex cost unknown. SAM/Odoo design, Node-RED hold and protected rules unchanged.
