# Sanitized Operational Summary of the Foundational Windance Chat

This document preserves the useful outcomes of the long-running Windance build chat. Credentials, API keys, bot tokens, passwords, private keys, OAuth material, confirmation codes, and obsolete trial values are deliberately omitted.

## What was built

- A multi-host Windance homelab centered on HAL, Herald, SAL, AL, SAM, Odyssey, TMA-1, TMA-2, and RefWeb.
- Key-based SSH access and an inventory/runbook for managed nodes.
- Node-RED monitoring, Cloudflare access, iMessage communications, scheduled reporting, and failure notifications.
- A Herald Agent Harness with named staff roles, durable tasks, vector memory, action routing, and evidence-oriented execution.
- Google Workspace Gmail and Calendar integrations with approval gates.
- Read-only Odoo reporting and specialized operational queries.
- A SAM touch schedule application with daily Odoo data, trainer filters/colors, completion commits, carry-forward behavior, vet/farrier workflows, weather, clock, kiosk operation, and historical reporting.
- A Second Brain that indexes approved business documents and structured knowledge.
- Research, Bible study, private counselor, email, calendar, business, network, archive, QA, and communications roles.
- Backup/restore materials and a private GitHub repository for disaster recovery.

## Lessons learned

- Long chat context is not a safe source of truth and can fail or compact.
- Hermes/model narration often confused intention with execution. Durable receipts and verification are mandatory.
- Node-RED deterministic flows have generally been more reliable than unconstrained agent promises.
- Agent availability, scheduler availability, and message delivery are distinct states and must be tested independently.
- New interfaces must route to the same named profile and memory or users experience identity fragmentation.
- Raw transcripts are unsuitable for repositories because early setup messages may contain credentials.

## William's working style

William communicates naturally, often by voice while driving. Systems should infer ordinary intent, ask only material questions, and use short driving-safe approvals. He values humor and personality but expects direct accountability and proof. He prefers local-first computing to control cost, with cloud escalation when needed for reliability. He wants proactive assistance, not theatrical promises.
